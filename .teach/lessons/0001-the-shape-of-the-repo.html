The shape of the repo

Six folders, one rule about which way the arrows point. Learn the rule and you can place any change without opening a file.

The problem this shape solves

Archie does two jobs that pull in opposite directions. Studio is a live editing app: drag in an image, draw on it, type a note. Viewer is a dead-static site: HTML and JSON on a dumb host, no server, works offline.

Both need to draw the same annotation on the same deep-zoom image, in the same place, with the same maths. Write that twice and it drifts — the region you drew in Studio lands three pixels off in the published site, and now you have a bug that only exists in one of them.

So the shared brains got pulled out into packages, and the two apps were forbidden from ever importing each other. Everything below follows from that.

The rule

Arrows point down only. core never imports mount. Neither app imports the other. When an agent hands you a diff that reaches upward or sideways, that's the structural smell to catch — it's how the two apps drift apart again.

Studio and Viewer do connect, but not through code: Studio's publish step writes the files Viewer reads. A build artefact, not an import.

Why core refuses to touch the browser

@render/core has no DOM in it — no document, no window, no canvas library. That sounds like purism; it's actually leverage. Three things fall out of it:

  • It runs anywhere. Same code in Studio, in Viewer's build step, in a Node script, in a test with no browser at all.
  • Its tests are fast and honest. No fake DOM to disagree with the real one.
  • It's the one place the data model is defined. Everything upstream speaks the types in packages/render-core/src/wadm/types.ts.

The trade is that core can't do anything visible. Showing pixels is mount's job; reacting to clicks is svelte's.

What you now know

Placing a change is mostly one question: does this need a browser? No → it's core. Yes, but it's pixels-and-events plumbing → mount. Yes, and it's "when this variable changes, tell the canvas" → svelte. Otherwise it's the app that owns the screen it appears on.
