Archie codebase · Lesson 4

What the browser will let you touch

Getting files in, and getting them back out. The File System Access API is really two APIs with completely different support — and that split is why Studio behaves the way it does.

The awkward fact

Archie's whole pitch is "no server." That means the browser has to hold real work — gigabytes of images — and hand it back as real files. Which runs straight into the thing browsers are most paranoid about: your disk.

So the File System API got built in two halves, and they landed in very different places. This is the single fact to hold:

OPFS — private storage, invisible to the user, scoped to your origin.
Baseline · widely available since March 2023
Works everywhere. No permission prompt — the user never sees it, because it isn't their filesystem.
The pickers — showDirectoryPicker, showOpenFilePicker, showSaveFilePicker. Reach into the user's actual folders.
Limited availability · still flagged experimental
MDN, today: "not Baseline because it does not work in some of the most widely-used browsers."

Same spec family, opposite realities. Everything Archie does about browsers follows from it: the private half is universal, so that's where the working copy lives; the real-disk half is a bonus, so it's an upgrade, never a requirement.

Why the pickers are slow, too

Not just rarer — heavier. MDN: writes through a picker handle are not in-place. The browser writes a temp file, runs security checks (Safe Browsing in Chrome), and only then replaces the original. Fine for a text file, painful for a 300MB folder of tiles. OPFS is the optimised path on purpose.

Archie's answer: never ask which browser

There is no user-agent sniffing anywhere in this codebase. Capability is probed, in exactly one module, and the result is never shown to the user as a limitation:

export function supportsFolderPicker(): boolean {
  return typeof window !== "undefined" && "showDirectoryPicker" in window;
}

apps/studio/src/binding.ts:16 — "This is the ONLY place capability is read — the user never sees it."

Four probes, layered, each naming the fallback beneath it:

  • supportsFolderPicker() — can we bind a project to a real folder?
  • supportsFileStreamSave() — is there a save picker to stream into?
  • supportsOpfsStagedZipSave() — no picker, but can we stage the zip in OPFS and hand the browser a disk-backed file to download?
  • supportsStreamingZipSave() — any of the above, or desktop.

Note the third one. It's a workaround with real teeth: a browser with no save picker can still stream a huge archive to disk, because OPFS is disk — write it there in bounded memory, then hand the download pipeline a File that's already on disk. No 4GB blob in RAM.

Three doors in, and the trap between two of them

Files reach Studio three ways, and they are not equivalent:

1. <input webkitdirectory> — the universal one

Works everywhere. Gives you a flat File[] where each file carries webkitRelativePath — "MyFolder/scans/f01.jpg" — which is how Archie knows which subfolder a file came from and what to name things. apps/studio/src/folder-import.ts:45

2. Drag-and-drop a folder — same idea, different API, one nasty gap

A drop gives you DataTransferItems; you call webkitGetAsEntry() and walk the tree yourself. And here's the bite:

The divergence that costs you an afternoon

FileSystemFileEntry.file() does not set webkitRelativePath the way an <input webkitdirectory> pick does. Same-looking File objects, one silently missing the property all the downstream grouping logic reads.

So the walker assigns it by hand, and there is exactly one walker in the codebase — both the page-level dropzone and the create-dialog dropzone go through it, precisely so this fix can't exist in one place and not the other. apps/studio/src/folder-drop.ts:1-9

That walker is also per-entry tolerant: a real drop can contain a file removed between drag and drop, or a directory the OS won't enumerate. One bad entry skips and increments a counter — it never rejects the whole walk. A drag-drop that half-worked must report "3 couldn't be added," not die silently.

3. showDirectoryPicker() — Chromium only, and different in kind

The other two copy files in. This one hands back a live, writable handle to a real folder — Archie keeps it as a binding, so saving writes back to your actual disk in place. That's a different product experience, not just a different code path, which is why it gets its own concept and its own module.

Two gotchas that make the picker fail for reasons unrelated to support

  • Secure context. HTTPS or localhost only. This is one more reason the dev front door is localhost:5173 and not a LAN IP — an IP address isn't a secure context, and the pickers would vanish on a browser that has them.
  • Transient user activation. The call must come from a real click. Do await somethingSlow() first and the activation can expire — the picker then throws SecurityError on a browser that fully supports it. Open the picker first, do the slow work after.

The principle worth stealing

Where support runs out, Archie doesn't disable a feature — it changes the shape of the feature so the product stays whole:

PlatformWhat "Save" means
ChromiumWrite back into the folder you bound. Like a native app.
Firefox / SafariSave downloads a .archie.zip. The Word-2003 model — your document is a file you keep.
DesktopNative dialog, native writes, no browser rules at all.

Neither browser user hits a wall reading "your browser is unsupported." They get a coherent, complete way to work that happens to differ. That's the bar — and it's only affordable because capability lives behind four booleans in one file instead of being scattered through the UI.

One more divergence, different layer

Importing by URL — a remote image or a IIIF manifest — isn't about the File System API at all. It hits CORS, which the browser enforces no matter how modern it is. A host that refuses cross-origin reads simply can't be imported from a web browser.

The desktop build escapes it: Tauri's native HTTP has no CORS, so images and info.json route through a native bridge instead. Same app, one genuine capability the web version cannot have. .claude/rules/tauri-csp.md

Support levels move. The two claims above — OPFS Baseline, pickers Limited — were checked against MDN on 2026-07-24. Re-check before repeating them anywhere public. This is also exactly why the code probes at runtime instead of encoding a browser table: the code doesn't go stale.
