Ports and the front door

Three ports in dev, zero in production. The gap between those two numbers is the whole design.

Start at the end: deploying has no ports

Worth getting this straight first, because it makes the dev setup make sense.

A deployed Archie is files. pnpm build:gh-pages produces a folder — gh-pages-dist/ — containing a landing page, studio/, and viewer/. You copy that folder onto GitHub Pages, Netlify, an S3 bucket, a USB stick. Nothing listens on a port. Nothing runs. There's no process to keep alive, nothing to restart at 3am, no server to be breached.

Ports exist only while you're developing, because dev servers need to watch files and push hot reloads. They're scaffolding. And scaffolding around a shape this specific gets awkward, which is why there are three of them.

Why three?

Archie is two apps. In dev each brings its own server, because they're built by different tools: Studio is Vite, Viewer is Astro. Left alone that's two origins — localhost:5174 and localhost:4321.

Two origins would work fine. It would also throw away the single best thing about the dev setup:

The payoff

The browser keeps your Studio work in OPFS — private storage scoped to an origin. Put both apps on the same origin and the Viewer can read the Studio's working store directly.

Which means: author an exhibit at /studio/, open /viewer/, and it's already there. No publish step. No export. You see what a visitor sees, live, as you type.

scripts/dev.sh:5 — "Same origin ⇒ the Viewer's live source reads the Studio's OPFS working store in dev."

To get one origin you need one door. So a third process — a ~45-line proxy — sits on :5173 and routes by path. That's the front door.

The routing rule, in full

const targetFor = (url) =>
  url.startsWith("/studio") ? "http://localhost:5174"   // Vite
                            : "http://localhost:4321";  // Astro

scripts/dev-proxy.mjs:21 — that really is the whole rule.

It's deliberately dumb. Anything starting /studio goes to Vite; everything else goes to Astro. That asymmetry works because Vite namespaces all its dev URLs under its base, so the one prefix catches its internals too — while Astro's internals live at root-relative paths and fall through the catch-all.

Click a URL. See where it lands in dev, and what it is in production.

Why not just make one server front the other?

Obvious first instinct — Vite and Astro both ship proxy config. Both were tried. Both fail, in different ways, and one of them fails dishonestly:

  • Vite can't front Astro. Astro asks for its dev internals at root-relative paths (/@vite, /@id, /src, /@fs). A /viewer-prefixed proxy never sees them.
  • Astro can't front Vite. Astro routes HTML navigations — anything with Accept: text/html — through its own router before its proxy middleware runs.
The bug worth retelling

That second one produces the nastiest symptom in this repo's history: curl /studio/ works perfectly. A browser visiting /studio/ gets a 404.

Same URL, same server, opposite results — because curl doesn't send Accept: text/html and a browser does. Every tool you'd reach for to debug it reports success.

scripts/dev-proxy.mjs:6 — "Found the hard way."

Two rules that look fussy and aren't

1. strictPort: true — fail loudly, never drift

Normally a dev server whose port is busy just takes the next one and prints a friendly message. Both servers here refuse to. If :5174 is taken, Vite dies.

Because the front door's targets are hardcoded. A server that silently moved to :5175 leaves the proxy pointing at nothing — and you'd get a 502 on a page that looks like it should work, with two healthy-looking servers running. A loud failure at boot is strictly better than a confusing one later. Kill the stale server, rerun. apps/studio/vite.config.ts:33

2. 127.0.0.1 — a literal, not localhost, never a wildcard

Two separate decisions packed into one line, and both matter:

Not a wildcard bind. The proxy forwards /studio/* to Vite unrewritten — including Vite's /@fs path, which serves arbitrary files from your disk. Binding to 0.0.0.0 would put your filesystem on the café wifi.

Not the word localhost. Passing a hostname to listen() sends it through dns.lookup — so which interface you actually bind to depends on the machine's resolver. The literal IP removes the question. scripts/dev-proxy.mjs:37

The port table

PortWhatNotes
5173Front door proxy The only one you type. / → 302 to /studio/
5174Studio (Vite) strictPort, base /studio/
4321Viewer (Astro) strictPort
5198Studio e2e tests Its own port so a running pnpm dev never collides. Override with STUDIO_E2E_PORT when two agents run tests at once.

One command starts the first three: pnpm dev → scripts/dev.sh, which boots both servers in the background and then runs the proxy in the foreground, with a trap that kills both children on exit.

Back to production: what replaces the proxy?

Nothing. A static host has no routing layer to configure, so the paths must be baked in at build time — that's what the build script's flags are doing:

vite build --base="/Archie/studio/"     # Studio's asset URLs
SITE_BASE="/Archie/viewer/" pnpm build  # Astro's

Get one wrong and you ship a page whose every asset 404s. So the origin has exactly one definition — archie.config.json — read by the build script, by Studio's share links, and by the Viewer's og-image and sitemap emitters. Changing domains is a one-file edit, and the build refuses to run if that origin doesn't match the repo name. scripts/build-gh-pages.sh:12

Three deployments, not two

There's a third thing that gets "deployed" and it's the one that matters to users: a published library. That isn't built by any of this — it's the folder Studio's publish step writes. Plain HTML, JSON, and media. Drop it anywhere. Or hand someone a single .archie.zip and they open it with no host at all.
