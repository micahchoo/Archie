Archie codebase · Lesson 2

Nothing is ever overwritten

The annotation spine. One decision — never destroy the old version — and everything odd-looking in spine/ falls out of it.

Two problems, one answer

Problem one: the citation. A scholar cites a note in your library — a footnote in a published paper pointing at it. You come back next year and reword that note. Their footnote now points at words that were never written when they cited it. Silently. That's not a bug you can fix later; it's a bug you can only avoid by design.

Problem two: the two zips. Archie has no server, so co-authoring means mailing a .archie.zip back and forth. Two people work on the same library for a week. Both edited note #47. Now what?

The tempting answer to problem two is "newest wins — compare timestamps." Archie refuses that, and the reason is worth memorising because it generalises:

Rejected: last-write-wins on the clock

Two machines' clocks routinely differ by 1–30 seconds. So the edit made later in real life can carry the earlier timestamp — and gets silently discarded. You get no error, no conflict, no card. Just work that quietly disappeared.

docs/adr/0003 · "Pure wall-clock LWW — rejected: clock skew silently loses the older-by-the-clock-but-actually-later edit."

Both problems have the same answer: an edit never replaces anything. It appends. The old version stays on disk forever. A delete isn't a deletion either — it appends a record with deleted: true, which the codebase calls a tombstone.

The bit that trips everyone: there are two ids

A note has a logicalId (this note, across all its versions) and each version has a rev. But versions also have a human-facing number — note-47/v3 — and that number is not what parent points at.

Why not? Because two people editing v1 at the same time both produce a "v2". If parent pointed at version numbers, a later record saying parent: "note-47/v2" would be ambiguous — which v2? So the DAG walks rev, a unique ULID minted per record, and the pretty /v3 number is kept purely as the citation label.

The analogy that makes it stick

This is git, exactly. rev = the commit hash. parent = the parent hash. {logicalId}/v3 = the tag — a human-friendly name for a commit, never the thing git actually follows.

The repo found this the hard way and amended the ADR mid-implementation (docs/adr/0003…md:35). Retelling tip: this is a good "we got it wrong and here's the failure that showed us" story.

So what's true *right now*?

If the log holds every version ever written, rendering the library means answering: which records are current? The rule is one line, and it's beautiful:

A record is current if nothing else claims it as a parent. Nobody has edited it, so it's the tip. The code calls these heads, and computing them is a single pass — spine/heads.ts:28.

Note the plural. Usually there's one head per note. After two people edit independently, there are two, and Archie renders both overlapping on the canvas rather than picking one. That looks like a bug and is a deliberate choice: showing you that two truths exist is honest; silently picking one is the data loss you were avoiding.

Drive it

Alice and Bob each have a copy of the same library. Append some edits and watch the heads recompute by the rule above.

Merging is a classification, not a decision

When two logs meet, Archie doesn't try to be clever per note. It sorts each note into one of three buckets — spine/merge.ts:140:

  • identical — same rev. Nothing to do.
  • fast-forward — one side's head is an ancestor of the other's. Only one person actually edited; take the descendant. No card, no question asked.
  • conflict — both moved on from a shared ancestor. Only now does a human get asked, in the Review Changes UI.

Most "conflicts" in real zip-swapping are fast-forwards in disguise — the two people touched different notes. That's the payoff of keeping ancestry: the machine resolves the boring 95% because it can prove which is which, and bothers you only for the genuine 5%. Timestamps play no part in this classification at all; modifiedAt is only ever shown to you inside a conflict card as a hint.

The three alternatives that lost

Keep these — they're the spine of the retelling:

  • Edit in place — kills provenance, breaks citations, makes ancestry impossible.
  • Every difference is a conflict card — throws away the common ancestor the log hands you free, so the human resolves everything by hand.
  • Just use git on the folder — line-diffing JSON is the wrong granularity for annotations, and it drags a terminal into a product built for people who don't have one. The parent chain gives you three-way-merge semantics without git.
