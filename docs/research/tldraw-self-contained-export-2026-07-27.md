# How tldraw makes a self-contained export, and what that implies for a single-file Archie exhibit

**Archie-5582.** Read at the source (`tldraw/tldraw` `main`, 2026-07-27), not summarised from memory.

## The pipeline, in the order it runs

`exportToSvg.tsx` is short and its shape is the whole lesson:

1. **Build a JSX SVG.** `getSvgJsx` asks each shape for a `toSvg`; a shape that has none is rendered
   as its normal HTML inside a `<foreignObject>`.
2. **Render it into the LIVE document, hidden.** A `<div class="tldraw-svg-export">` is appended to
   the editor container, `inert`, `tabIndex = -1`, `opacity: 0`, `pointerEvents: none`, positioned
   absolutely at the export's size. The comment says why in one line:

   > "we have to add the element to the document as otherwise styles won't be computed correctly."

3. **Harvest computed styles and resources** while it is still in the document (`StyleEmbedder`,
   `FontEmbedder`, `embedMedia`).
4. **Detach.** Only then is the SVG pulled out as a standalone artifact.

**Step 2 is the load-bearing idea and the one worth stealing.** A self-contained export is not
produced by *serialising a model* — it is produced by *rendering the real thing and then
photographing everything it depended on*. You cannot know which fonts, which CSS custom properties,
or which `url()` references matter until the browser has resolved them, and the browser will only
resolve them for an element that is actually laid out.

## The three embedders

**`StyleEmbedder`** walks the tree and records each element's *computed* style — plus `::before`
and `::after`, which a naïve serialiser drops entirely. Two economies keep the output from exploding:

- `shouldRespectDefaults` — a child's property is skipped when it equals the tag's default (obtained
  by measuring a throwaway element of that tag).
- `shouldSkipInheritedParentStyles` — walk up the ancestors and skip anything that would inherit
  anyway.

The root is the exception: it gets *all* styles unconditionally, because it has no parent to inherit
from. Every recorded value is then scanned with `parseCssValueUrls`, and each `url()` becomes a data
URL via `resourceToDataUrl`.

**`FontEmbedder`** is a three-phase collector, and the phasing is the interesting part:
`startFindingDocumentFontFaces(doc)` harvests every `@font-face` in the document (following
`@import`); `onFontFamilyValue` is called *by StyleEmbedder as it walks*, so only families actually
used get marked; `createCss()` awaits the in-flight fetches and emits `@font-face` blocks with the
`src` URLs textually replaced by data URLs. Fetches start the moment a family is seen, not at the
end — the walk and the network overlap by construction.

**`embedMedia`** replaces by element kind: `<canvas>` → `toDataURL()`; `<video>` → a frame grab,
falling back to its `poster`, falling back to `data:`; `<img>` → `currentSrc` to a data URL. Two
details worth copying: it uses **`currentSrc`**, so a `srcset`-resolved image embeds the variant the
browser actually chose; and it awaits `image.decode()` with the failure swallowed, so a rasteriser
downstream never catches a half-decoded image. It also fixes form state that lives only in the DOM
(`input.value` → the `value` attribute, `textarea.value` → text content), which serialisation loses
silently.

## What this implies for a single-file HTML Archie exhibit

**The good news: Archie's artifact is already much closer than tldraw's was.** The published static
page is *already* self-contained in structure — one HTML file, no script, a single inlined `<style>`
constant, and no external stylesheet. Three things stand between it and one file:

| dependency | count today | fix |
|---|---|---|
| object images (`<img src>`, IIIF or `assets/`) | the bulk of the bytes | data URL per image |
| the `og:image` / JSON-LD URLs | metadata only | leave absolute — a citation must resolve |
| fonts | **none** — the page uses `system-ui` | nothing to embed |

That third row is why the tldraw font machinery, the most intricate part of its pipeline, is **not**
needed here: `static-pages.ts`'s `STYLE` names `system-ui, -apple-system, "Segoe UI", sans-serif` and
loads no web font at all. A single-file exhibit export is therefore *image inlining plus what already
exists*, not a port of this pipeline.

**And Archie does not need step 2 either.** tldraw must render-then-photograph because its shapes are
React components whose styling lives in stylesheets it cannot enumerate ahead of time. Archie's
static page is generated by `exhibitPageHtml` from the model, with one known `STYLE` constant — the
computed-style harvest has no work to do. Taking the tldraw pipeline wholesale would be importing a
solution to a problem this codebase does not have.

**What IS worth taking, concretely:**

1. `embedMedia`'s `currentSrc` rule, if a single-file export is ever built — Archie's grid emits
   sized IIIF derivatives, so the resolved variant is the one to inline.
2. The `image.decode()`-before-snapshot discipline.
3. The idea that a self-contained artifact should be *verified* self-contained, not assumed: tldraw
   gets this free (an SVG that still references an external font simply renders wrong), and Archie
   would not. A single-file export needs a gate that loads the artifact **with the network cut** and
   asserts every image painted — the same shape as the viewer's existing `goOffline` e2e specs.

**Cost, stated honestly:** a data-URL export inflates bytes by ~33% (base64) and is unstreamable — a
1,000-image exhibit becomes one unopenable file. So this only makes sense as a *small-exhibit*
affordance, which is exactly how `Archie-c34f` ("Prototype: single-file Archie exhibit export")
scopes it. This research does not recommend building it; it removes the unknowns so that ticket can
be a half-day rather than an investigation.
