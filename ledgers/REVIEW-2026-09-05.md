# Archie: code review and product recommendations

Reviewed 2026-09-05. Snapshot: `91935b2`, with the existing working tree. Review only; no production fixes applied.

**Recommendation: make the next release a reliability and reader-consistency release.** Archie has a coherent purpose, substantial implementation, and useful architectural boundaries. Its most consequential remaining problems concern whether an author's work survives, whether a citation opens the intended interpretation, and whether an explicit offline setting prevents resource loading. Those promises deserve priority over additional media types or reading modes.

This review identifies **13 findings: 4 P1 and 9 P2**. P1 means address before the next release relying on that capability; P2 means a reproducible functional, accessibility, or verification defect. These are snapshot findings, not claims that the latest commit introduced them. The two review axes remain separate below: implementation/standards and product contracts. Product recommendations follow the evidence.

## Implementation and standards findings — 8

### S1 · P1 · An edit made during save can disappear after two successful saves

**Location:** [session.ts:327](../packages/render-core/src/session/session.ts#L327), with the full-save variant at line 320. Production caller: `apps/studio/src/exhibit-session.svelte.ts:69`.

`save()` snapshots dirty note IDs, awaits writing the current log, then deletes those IDs from the live dirty set. An additional edit to the same note during the await is indistinguishable from the revision already saved. The full-save branch clears the entire dirty set after awaiting, creating the same problem.

**Reproduction:** block the first filesystem access, edit the note, release the save, complete a second save, then reload. Full-save case: memory had the new body and two versions; disk reloaded `v1` and one version. Incremental case: memory had three versions; disk reloaded `v2` and two versions. Serializing save calls does not serialize edits against saves.

**Change:** acknowledge the specific revisions written, or drain pending changes before awaiting and restore them on failure. Cover full saves, incremental saves, merges, and additional edits during the write.

**Acceptance:** after an edit during any save, a subsequent completed save/reload preserves that edit and all version history. Evidence: `archie-review-data-results.log`.

### S2 · P1 · Archive/folder adoption silently drops unreadable notes

**Location:** [site.ts:1146](../packages/render-core/src/publish/site.ts#L1146); destructive adoption downstream at `apps/studio/src/ingest-flows.ts:1218`.

`loadLibrary()` uses `readAnnotations()`, which discards the reporting reader's corruption diagnostics. A committed history page can be missing or unreadable while the library marker still validates. The resulting partial library is treated as healthy and can replace the existing working library.

**Reproduction:** publish two notes, remove one referenced history page, validate the marker, then load the library. Validation succeeds; one note is returned with no warning. The reporting reader separately identifies the missing page.

**Change:** carry corruption through the load result and require a deliberate recovery decision before replacing working data. Preserve the original input for recovery. A structurally valid archive must not imply complete content.

**Acceptance:** an archive with a missing committed note page cannot be silently adopted or exported as complete. Evidence: `archie-review-publish-results.log`.

### S3 · P2 · A wrong-shaped JSON page defeats per-page recovery

**Location:** [persist.ts:132](../packages/render-core/src/spine/persist.ts#L132), and conversion at line 140.

The individual page catch covers file reading and JSON parsing. Conversion to annotation records happens afterward, outside that catch. A valid JSON object with no `items`, such as `{}`, throws globally and prevents recovery of healthy siblings.

**Reproduction:** replace one of two saved note pages with `{}`. `readAnnotationsReport()` throws `TypeError: page.items is not iterable`, instead of returning the intact note and one diagnostic.

**Change and acceptance:** validate and deserialize inside each page's failure boundary. Test wrong schema as well as invalid JSON and missing files. The structure reader already places its conversion inside the per-page catch; align the mechanics. Evidence: `archie-review-data-results.log`.

### S4 · P2 · An inaccessible history directory is reported as clean and empty

**Location:** [persist.ts:103](../packages/render-core/src/spine/persist.ts#L103) and [structure-persist.ts:95](../packages/render-core/src/spine/structure-persist.ts#L95).

Both readers catch every history-directory lookup error and return an empty log with no corruption. Permission revocation and I/O failure do not establish absence. Downstream initialization therefore loses the information needed to avoid treating inaccessible work as a fresh project.

**Reproduction:** `getDirectory()` throws `NotAllowedError`; both readers return `{log: [], corrupt: []}`.

**Change and acceptance:** only a classified not-found error may become empty. Other failures must retain their meaning through callers. Test not-found, permission failure and generic I/O failure separately. Evidence: `archie-review-data-results.log`.

### S5 · P2 · Studio never separates undoable user actions

**Location:** [undo-wire.ts:79](../apps/studio/src/undo-wire.ts#L79); button promise at [UndoControls.svelte:17](../apps/studio/src/UndoControls.svelte#L17).

The manager groups mutations between `mark()` calls. Production Studio code never calls that method. Its tests explicitly insert marks, so they verify a capability that the actual wiring omits. The button promises to undo the last note change.

**Reproduction:** make two note creations through the manager using the unmarked sequence emitted by Studio, then undo once. Both notes disappear from the projection and `canUndo` becomes false. A create followed by delete can squash to no history at all.

**Change:** define user action boundaries: note creation, deletion, completed drag, completed import, and a deliberate text-edit grouping policy. Bind those boundaries at the command or gesture seam.

**Acceptance:** two separate note creations require two undo actions; one region drag is one action. Test through the production wire without manually supplying missing behavior. Evidence: `archie-review-undo-results.log`.

### S6 · P2 · Editing after undo diverges from the visible note

**Location:** [undo.ts:127](../packages/render-core/src/session/undo.ts#L127), also deletion at line 138.

Undo applies a projection overlay, but normal edits read and mutate the underlying log head without reconciling the overlay. After undoing an edit, a subsequent edit can persist while the screen continues showing the old body. After undoing deletion, the UI displays a restored note whose underlying head remains tombstoned.

**Reproduction:** edit `original` to `edit1`, undo, then edit to `edit2-after-undo`. Stored body becomes `edit2-after-undo`; visible body remains `original`. Separately, delete a pre-existing note, undo, then edit it: the session throws `cannot edit a tombstoned note`.

**Change:** define one authoring truth after undo. Reconcile changes against the state the user sees, including restored deletions. Keep prior revisions immutable, and explicitly decide how any compensating record is represented.

**Acceptance:** an edit following undo changes the visible note immediately and has defined save behavior; a visibly restored note is editable. These defects are separate from the accepted decision that the undo overlay does not survive closing an exhibit. Evidence: `archie-review-undo-results.log`.

### S7 · P2 · The required workspace typecheck is red

**Location:** [fake-opfs.ts:88](../apps/viewer/src/fake-opfs.ts#L88).

The test helper iterates an `FsDirectory` directly, but the filesystem seam exposes `entries()` rather than an async iterator on the directory itself. The TypeScript diagnostic is TS2504. This is a test-support defect that blocks the workspace check, not evidence that the production Viewer always crashes.

**Change and acceptance:** iterate the seam's declared entry stream and rerun the workspace typecheck plus the live-source tests that use this helper. Preserve the helper's output as FSA-style `[name, handle]` pairs. Evidence: `archie-review-types.log`.

### S8 · P2 · Shared muted text colors fail contrast on actual surfaces

**Location:** [tokens.css:61](../packages/render-core/src/tokens.css#L61) and paper variants at lines 71–72; consumers include `ExhibitOverview.svelte` and Viewer's gallery.

On the Studio overview, 19 elements failed the sampled axe contrast rule. Examples were 2.45:1 for small muted labels and 3.75:1 for save status. The mobile gallery had eight failures, including 3.85:1 description text. These were real-browser measurements, not a visual impression from screenshots.

**Change:** adjust semantic text tokens against their actual backgrounds, then check affected controls and content. Preserve the warm green/cream palette. Existing `a11y:check` targets published static pages; the Viewer inert tests target a different accessibility property. Neither establishes contrast in these app states.

**Acceptance:** ordinary small text reaches 4.5:1 on the sampled surfaces, and the same fixtures become regression checks. This threshold follows [WCAG contrast requirements](https://www.w3.org/TR/WCAG22/#contrast-minimum). Status changes should also remain available to assistive technology under [WCAG status messages](https://www.w3.org/TR/WCAG22/#status-messages). Evidence: `archie-review-ui.log` and screenshots.

**Axis total: 8 findings; highest severity P1, affecting save durability and safe import.**

## Product-contract findings — 5

### C1 · P1 · Offline embeds still emit remote cover and note-media sources

**Location:** [element.ts:855](../packages/archie-viewer/src/element.ts#L855); note-media sinks include [note-card.ts:247](../packages/archie-viewer/src/note-card.ts#L247).

The primary object loader observes offline mode, but gallery covers and note media create live HTTPS image/audio/video sources without that policy. An archive can put a remote cover on the first gallery screen before any primary object opens. ADR-0021 describes offline as an egress safeguard; the public documentation does not exempt these resources.

**Proof:** a source-bundled happy-dom probe opened a published MemoryFilesystem with `offline=true`. Its shadow DOM contained `https://tracker.test/pixel.png` as an image source. The note-card renderer similarly emitted a remote note image. This proves the ungated resource assignment; this review did not send a tracking request or measure actual network egress.

**Change and acceptance:** apply one resource policy before every fetch-capable DOM assignment, including covers, thumbnails and note bodies. Use an actual browser fixture with intercepted remote requests to assert zero disallowed requests. Define what changing offline mode during a read means.

### C2 · P2 · Reading-specific citations resolve as missing

**Location:** [target-resolve.ts:72](../packages/archie-viewer/src/target-resolve.ts#L72); related search opening at `element.ts:625`.

The target resolver searches base annotations but omits per-Reading annotations. This contradicts ADR-0021's promise that opening a note activates its Reading. Search includes those notes, but its arrival path likewise lacks the required Reading activation.

**Proof on shipped data:** the Cipher note `000000000C5M05B5H33KBKENTM` on Voynich object `ex-voynich.o1` resolves to `{kind:'exhibit', degraded:'note-not-found'}`. The note exists in the generated published tree.

**Change and acceptance:** resolve an address to object, note and Reading together, activate that Reading, then mount/select. Run the same resolution for a copied target and a search hit. Test a note present exclusively in one Reading.

### C3 · P2 · Whole-recording AV citations do not open their note body

**Location:** [av-player.ts:334](../packages/archie-viewer/src/av-player.ts#L334).

Initial selection looks only through timed cues. A note about an entire recording has no cue range, so it reaches the early return without opening its card. The generic note address is valid, but the content it cites stays hidden.

**Proof:** mounted the real AV controller with an untimed annotation and matching `initialSelect`, then dispatched `loadedmetadata`. The note card remained hidden.

**Change and acceptance:** resolve note selection from all annotations independently of an optional seek time. A whole-recording citation opens the body while leaving playback paused; a timed citation retains its seek behavior.

### C4 · P2 · An obsolete embed navigation overrides the newer gallery target

**Location:** [element.ts:404](../packages/archie-viewer/src/element.ts#L404), with sequence checking at lines 423–426.

Gallery and unknown-slug transitions do not invalidate a pending exhibit load. A host can set an object target and then set the gallery target, yet the old asynchronous load later paints the object.

**Proof:** two immediate target assignments over a real in-memory published library produced `{target:'#/', renderedReader:true, renderedTitle:'Audio'}` after completion.

**Change and acceptance:** every target transition supersedes previous work and tears down the old surface. Check ownership after asynchronous loading and mounting. Rapid object→gallery transitions must finish at the gallery.

### C5 · P1 · An external-library address can reload into a different library

**Location:** [ExhibitView.svelte:228](../apps/viewer/src/components/ExhibitView.svelte#L228), writing the replacement hash at line 246; gallery links also require review.

The Viewer supports `?src=` in its hash route, but its locus writer builds a fresh route without the source. The external library stays in memory, masking the problem until someone reloads or shares the rewritten address. If the default library contains the same slug, the visitor can see a different exhibit under that address.

**Real-browser reproduction:** intercepted a local foreign-tree URL backed by the bundled files, changing the exhibit title to `FOREIGN ROSETTES`. Opened its supported source URL and waited for the locus rewrite. The URL lost `src`; refreshing then showed the default `The Rosettes`. No external host was needed. This confirms the candidate described in the reader appendix.

**Change and acceptance:** make the active source shell-owned address context. Preserve it through navigation, locus writes, degradation and citation copying. A foreign library with a slug colliding with the default must retain its title and content after navigation, copy/open and refresh. Evidence: `archie-review-source-results.log`.

**Axis total: 5 findings; highest severity P1, affecting offline behavior and source-preserving publication links.**

## Product management: choose the next release around author trust

The product's strongest proposition is a small complete loop: bring primary-source media, add an interpretation, and publish something portable and citable. The architecture and working surfaces support that proposition. README currently addresses many different personas; this review supplies no market evidence that all those audiences deserve equal investment.

**Recommended initial focus, as a hypothesis:** individual scholars and small curatorial teams preparing a citable exhibit. Validate it with actual users. These users directly exercise Readings, notes, attribution, open formats and portable publishing. Expansion into other segments can follow evidence from that loop.

| Priority | Product decision | Why now | Observable success |
|---|---|---|---|
| First | Finish the reliability release | Save loss and silent partial adoption undermine the central ownership promise. | Save during editing, reopen, recovery import and citation round trips pass the new failure fixtures. |
| Next | Define one activation outcome | Feature completion and test totals do not establish that a new author can finish useful work. | An unassisted author imports their own media, adds a note, reopens it, and gives another person a working publication. |
| Next | Publish a capability matrix | Browser authoring, desktop, Viewer, embed, static pages and portable files have different guarantees. | Each advertised capability names supported delivery modes and has corresponding evidence. |
| Later | Fund the next feature from observed blockage | More modes expand the interaction and testing surface. | A repeated user obstacle, a specific target cohort and a measurable task improvement justify the feature. |

Measure completion of that activation task, time to first useful annotation, successful save/reopen, and whether a recipient reaches the cited note. Start with observed sessions or opt-in diagnostics; always-on analytics are unnecessary for this local-first product. Establish baselines before inventing conversion targets.

Treat desktop verification and large-library resource limits as explicit release work. The hubs document packaged desktop gaps and a historical 16.9GB publish peak; these were not reproduced here and must not be reported as new measurements.

## Product design: make ownership, actions and content easier to read

The visual system has a recognizable character, and the creation dialog offers a comprehensible three-path choice. The mobile gallery reflows without horizontal overflow. Preserve those strengths.

1. **Make save status describe its destination.** On a first visit, the page shows `Saved`, `Living in this browser`, and examples whose edits are not retained. All have contextual explanations, but they require readers to combine separate messages. Test whether authors can correctly answer where their work lives and whether it will survive closing. Keep the existing unified status surface; make its state and destination legible together.
2. **Fix contrast before changing the visual identity.** Darker semantic text tokens are a small change with broad benefit. Do not sacrifice necessary metadata to achieve visual quiet. Check actual backgrounds rather than treating an alpha value as a contrast guarantee.
3. **Give authored titles room to identify their objects.** The sample overview displays fragments such as `Big Buck... a frame` and `Kryptogr... nscript`. Middle truncation is deliberate and useful for filename suffixes, but descriptive titles need a different treatment. Test two-line authored titles or a responsive card minimum before changing the established filename policy. Location: `ExhibitOverview.svelte:1155`.
4. **Bring the first meaningful item earlier on mobile.** In the 390px gallery screenshot, heading and explanatory copy place the first card title near the bottom of the initial viewport. Test a shorter summary with expansion so visitors can identify an exhibit sooner. Measure discovery success, not just scroll distance.
5. **Make undo correspond to a visible completed action.** Correct S5/S6 first. Then test whether the session-only disclosure is understood. The fact that undo history disappears and the fact that an undone effect can reappear after reopening are different expectations. This is an accepted product decision to evaluate, not an additional defect count. Any change needs an explicit amendment to that decision.

Suggested usability session: ask a new author to create an exhibit, annotate two items, undo one action, close/reopen, publish a copy, and have a second person open a Reading-specific citation. Observe uncertainty and errors before explaining the model. Include keyboard-only use and at least one user who benefits from stronger text contrast.

## Solutions architecture: deepen the boundaries that failed

Keep the headless core → mount → Svelte layering, the Studio/Viewer separation, the append-only history, the filesystem seam, and static publication. These choices serve the product. The evidence supports focused changes within them.

| Boundary | Concrete change | Failure it prevents | Constraint |
|---|---|---|---|
| Durable note persistence | One operation owns the write snapshot, revision acknowledgement, dirty restoration, and corruption result. | S1–S4: callers cannot equate an awaited write with every current edit being durable. | Keep incremental performance; do not copy the entire log on every edit. |
| Editor commands | One command boundary declares action grouping and reconciles undo with the visible state. | S5–S6: history behavior cannot depend on every UI handler remembering marks or overlay rules. | Keep prior records immutable; specify the semantics of restored deletion. |
| Reader address resolution | Resolve source + exhibit + object/note/section + Reading into a complete arrival description. | C2, C3, C5: valid citations cannot lose their source or required layer. | Keep the frozen public attribute contract and permitted presentation differences. |
| Reader navigation lifecycle | A navigation owner controls cancellation, sequence invalidation and teardown for every destination. | C4: stale async work cannot repaint the screen after a newer request. | Check later lazy-import/mount continuations as well as data loading. |
| Resource loading | Pass one explicit resource policy through covers, primary media and note rendering. | C1: a resource sink cannot accidentally bypass offline restrictions. | URL sanitization and permission to make a network request are separate checks. |
| Publication to a destination | Separate content planning from sink commit semantics where in-place writes need it. | Makes generation completeness, cleanup and failure recovery explicit. | Zip/Git and an in-place folder do not have identical atomicity. Avoid promising snapshot isolation from marker-last alone. |

Share annotation/structure page-store mechanics only where the contracts are actually the same: classified lookup failures, page-level recovery and commit ordering. Keep their codecs and domain behavior separate. Introduce no general plugin framework to accomplish this.

A small shared set of reader contract fixtures would have high value: a base note, Reading-only note, untimed recording note, external-source slug collision, hostile remote cover in offline mode, and two rapidly superseding targets. Run the applicable fixtures against each reader. Share expected semantics before attempting to share all rendering code.

## Complexity consulting: reduce the number of places a rule must be remembered

Raw file length is not the problem by itself. It directs attention to modules that coordinate many reasons for change: `App.svelte` is 3,178 lines; `CreateExhibitDialog.svelte` 1,809; `Publish.svelte` 1,485; `ingest-flows.ts` 1,354; `publish/site.ts` 1,212. Existing extraction work has already created useful seams such as the editor model and publish machine.

The recurring pattern is that a guarantee exists in a comment, test helper or low-level API but disappears when composed: mark-based undo without production marks, tolerant reads with discarded diagnostics, source-aware route serialization called without a source, offline object loading beside unrestricted cover loading.

**Recommended subtraction:**

- Retire or quarantine legacy publish routes after checking reachability. Do not maintain several deployment interfaces merely because they exist. The core appendix identifies a legacy GitHub adapter concern that needs reachability verification before being called a current user failure.
- Move historical narratives out of hot source files where they obscure current invariants. Retain the operative contract and a durable link to its decision/probe. Do not remove warnings that explain real failure modes without preserving the protection.
- Consolidate a rule only after identifying multiple sites that implement the same rule. Avoid a broad `utils` extraction that reduces line count but leaves the same coordination burden.
- Require a future feature proposal to name the state combinations it adds: medium, storage backend, delivery surface, Reading state, and pending async work. Test meaningful intersections, not the full Cartesian product.

Track the number of call sites that must change to add a note field, a reader resource kind or a publish destination; regressions crossing package boundaries; and the cost of the small contract fixture suite. These are more informative than a target for fewer files or fewer lines.

## Recommended delivery order

| Order | Work package | Relative size | Completion gate |
|---|---|---|---|
| 1 | Correct the typecheck helper and contrast tokens | Small, subject to visual regression review | Workspace TypeScript green; sampled contrast failures resolved. |
| 2 | Fix save acknowledgement and import/recovery diagnostics | Medium; highest data-integrity priority | S1–S4 fault probes pass as regression tests; original data survives a failed operation. |
| 3 | Repair undo grouping and post-undo authoring | Medium to large because semantics need care | Production-wire action tests and edit→undo→edit/delete→undo→edit browser scenarios pass. |
| 4 | Close offline and reader address/lifecycle gaps | Medium across several consumers | C1–C5 fixtures pass, including browser request interception and external-source refresh. |
| 5 | Run the first-use study and packaged desktop smoke | Scope depends on recruiting and packaging | Evidence for activation, storage comprehension, citation success and actual desktop flows. |
| 6 | Extract the proven boundaries and consider the next feature | Incremental | Fewer duplicated rules, existing contracts remain green, and a measured user obstacle motivates expansion. |

Relative sizes are planning judgments, not delivery estimates. A maintainer should re-estimate after choosing the undo semantics and recovery result shape. Product research can run alongside engineering; the reliability release gates remain sequential dependencies for claiming those capabilities are complete.
